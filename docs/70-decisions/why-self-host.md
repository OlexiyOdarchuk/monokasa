# ADR · Чому self-host, а не SaaS

## Контекст

Початково думали робити monokasa як SaaS (multi-tenant, наш дашборд,
платник = organizer, але через наш проміжний рахунок). Швидко
відмовилися.

## Рішення

**Один інстанс = один organizer. Платежі прямо на банку моно
organizer'а. Ми не дотягуємось до чужих грошей, не зберігаємо чужі
персональні дані, не маємо доступу до жодної чужої БД.**

## Чому НЕ SaaS

### Безпека / довіра

Multi-tenant ticketing вимагає:
- зберігати персональні дані тисяч покупців (PII)
- проходити через нас гроші (PCI-DSS-like compliance)
- вибудовувати ізоляцію tenant'ів у БД (RLS, scoped queries, аудит)

Кожна з цих фічей варта серйозного інженерного бюджету. Для проєкту,
де я хотів швидко рішення для невеликих українських подій — це
overkill.

### Бізнес-модель

SaaS вимагає платної підписки → biling → support → юридична сторона
(ТОВ, договори оферти). Для self-host цього всього не треба:
organizer піднімає свою копію, платить за хостинг ~$5/міс, далі ні з
ким нічого не ділить.

### Регуляторика

В Україні платіжна інтеграція через monobank-jar — без статусу
платіжної установи. Як тільки гроші проходять через нас → стаємо
посередником → ліцензія, фінмоніторинг. Не треба.

### Технічна простота

Self-host = SQLite. SaaS = Postgres з RLS, з підписками на оновлення
схеми, з резервним копіюванням, з масштабуванням. Кожен крок забирає
тиждень, який не йде в product value.

## Що ми втрачаємо

- "Підняв сайт, через 5 хв продаю квитки" — у нас треба підняти Docker.
  Друзня alternative для нетехнічних: купити VPS з готовим імеджем.
- Централізоване оновлення для всіх organizer'ів. У нас — кожен
  оновлюється сам.
- Аналітика across tenants — нема такого поняття.

## Що ми отримуємо

- Жодного access до чужих коштів і даних → жодних законних претензій.
- Прямий шлях гроші → квиток, без посередника.
- Простота: один бінарник, одна БД, один volume.
- Organizer бачить кожну транзакцію у власному акаунті моно.

## Альтернативи що НЕ використали

- **OAuth до monobank Acquiring API** — для еквайрингу. Тоді ми б
  отримували платежі, перенаправляли. Дорого, складно, мало кому
  потрібно.
- **Postgres + RLS** — multi-tenant SQL із row-level security. Працює,
  але повертає до проблем зверху.
- **Кожен organizer — окрема DB у нашому Postgres** — все одно ми
  господарі даних, проблеми ті ж.

## Підтвердження

Будь-який запит "а як зробити, щоб два organizer'и на одному інстансі?"
→ "Ставимо ще одну копію в Docker з іншим портом і .env. Це і є
відповідь."
